## Skipped, partial, or different from the brief

- **No separate "answer" AI call.** Every tool phrases its own result in code, so the loop makes none. The plan may carry a short `reply`, which is verified and dropped when a figure fails. This keeps requests at 1 to 2 calls.
- **Hand view controls** (Hide, Change) are not on the Data, How files connect, What we cleaned, How we analysed, Power BI export and Chat tabs. Their items are in the catalogue, chat view edits on them are saved, and hidden items are honoured only for cleaning steps and plan questions or analyses (with the Hidden items bar); the other tabs ignore hide.
- **Briefs in the interface:** PDF, Copy as text and Delete buttons; rename and edit are by chat only.
- **Custom analysis draws no chart**, only a table.
- **A cross-check runs only when the plan supplies a closed-operation query** (`check_query`); code does not search for one itself.
- **The sample run is shared on a server**, so briefs and feedback made on it are stored in its folder like the existing chat history.
- **Docker image not built.**

## Decisions

- **The request-type routes are now tools, and the plain-rule router is only the no-AI fallback** (`fallback_plan`). With an AI, only chips, `undo`, `reset the view` and hide or show by an exact item title skip the plan call.
- **Old single-action replies are still read** (as a plan of one step), so existing scripted tests keep working; the prompt asks only for plans.
- **Tests changed because a rule route was removed (with an AI present these requests now go to the planner, so they cost one plan call):** `test_lens_fixpack.py::test_graph_is_wrong_rechecks_the_latest_chart` (scripts a recheck_chart plan, 1 call), `test_view_changes_are_not_summarised` (no-AI path unchanged and asserted; with an AI an empty plan is asserted not to be a summary), `test_lens_stage2a.py::test_a_view_change_is_not_refused_as_a_data_question` (one plan call each; styling still gets view-change chips). Nothing else in the existing suite needed changing.
- **A step may depend on an earlier step:** plan validation knows the plan's other steps (an export of a brief written in the same request is valid), and `chart_edit` uses a chart drawn earlier in the same request.
- **One Undo per request:** view edits in a request rewrite the history so undo returns to the state when the request began.
- **Brief writing calls are on top of the 2-call budget** (one per brief, up to 4 briefs), as the brief asks for 2 calls per brief.
- **View commands gained groups:** hide or show every item of a kind, optionally in a tab or section.

## Fixes from real-AI testing (second round on this branch)

**Result:** frontend build passes; full backend suite **983 passed, 0 failed, in 307.48 s (5 min 7 s)** (includes the 14 new tests in `test_fixes_real_ai.py` and the browser test).

All six are general mechanisms; the example requests are only in `backend/tests/test_fixes_real_ai.py`. Fake AI only.

1. **Selector view changes.** Every item now has `type`, `measure`, `dimension`, `title`, `rank` (within its tab and type, in the report's own order) and `cited` (an action or the summary cites it); `viewselect.py` resolves a selector (type, tab, section, measure, dimension, title words, position, rank, cited, ids) to ids, so a command can touch any number of items. `hide`, `show` and `pin` take `select`; the new `keep_only` takes a `scope` selector and a list of things to keep, each with an optional `best` N (a chart an action or the summary cites comes first), and hides the rest of the scope. "Keep one graph about one measure and the others by another" is one `keep_only` command. A selector that matches nothing says what exists ("There are 19 charts about Revenue (13), Discount pct (4), by Segment, Region"). A change that would hide or show more than 3 items is **previewed** ("I will keep: ... and hide: ...") with an Apply chip that carries the same change as explicit ids; Undo and Reset are never previewed; one Undo reverts the applied change.
2. **Plain language.** Steps in "How this was calculated" and in "I stopped at step 2" use plain labels (`registry.plain`), the refusals no longer mention buttons that do not exist or "view change" jargon, and the PDF error no longer mentions a setting. A test scans every string passed to a message sink in the code (AST) and runs 18 failure cases plus 5 no-AI cases through the chat, and fails on a tool name, "command", "plan", "schema", "JSON", "registry" or any `snake_case` identifier.
3. **Relevant suggestions.** `agent/suggest.py` classifies a refused request as view, data or other from its own words and the report's columns and values; view requests get view examples, data questions get close data questions, anything else gets general report requests. The wording of the offer follows the kind. A missing cost column no longer refuses a request to change the view (the margin check now skips view requests).
4. **Summary scope.** `summarise` takes `scope` (only what the user named); nothing named means the whole report and the answer says "Summary of the whole report."; a tab, a section or a topic named means only that (fact tabs keep the AI wording and every figure check; other tabs and the ideas use the report's own records). The planner prompt says the open tab is never a scope; the no-AI router reads the scope from the words after "summarise". `reports.answer_summary` lead lines changed accordingly.
5. **Superlatives.** `agent/superlatives.py` checks AI-written summary and brief lines against the report's computed top and bottom of each measure and grouping level: a wrong direction is dropped, a missing level is added ("Clothing category brings in the most..."), and a later line that names a different group for the same claim, measure and level is dropped; a reworded summary line is re-verified. The report's own sentences are never altered. One existing assertion changed (`test_summary_lines_are_short_plain_sentences_and_still_checked`) because the level is now named in the line.
6. **Fewer suggestions.** Opening chips: at most 3 with an AI (a view example written from the tab's own sections or items, a data question chosen by what the tab is about, a summary), at most 4 without, chosen by tab and by the last question, with the rest behind a small "More ideas" link; after an answer at most 3; the no-AI "Without an AI model ..." reply shows at most 4 plus "More ideas". The old teaching chips are gone: the opening chips are removed from the panel as soon as the first message is sent. Typed words that read like a change to the view are no longer matched to a chip made for another tab ("Make this tab shorter" means the tab that is open).

Existing tests changed: `test_lens.py` (the opening chips are few, so the tests pick the data chip from the opening and "More ideas" lists), `test_agent_loop.py` (step and failure wording; a data chip rather than the first chip), `test_partb_view.py` (the new refusal sentence), `test_lens_fixpack.py` (level named). Bug fixed on the way: an Undo typed in chat without an AI was applied but not saved when it emptied the history.

**NOT tested with the real AI:** whether a real model writes valid selectors and `keep_only` commands from phrases like the one in item 1; whether it leaves `scope` empty when only a tab is open; how often the superlative check drops a real summary line; whether the view example and data chips read well on every tab; and the bulk preview wording with long real titles (the list is cut at 8 titles).


## Fix: questions about what is in the data (third round)

**Result:** frontend build passes; full backend suite **1004 passed, 0 failed, in 313.95 s (5 min 14 s)**.

A request such as "does the data have any information about <a concept>?" was refused with the generic "I can't answer that from this data" and a paragraph of abilities, because nothing could look at what the columns hold. General fix, no concept, column or value in the code:

0. **Data card** (`agent/datacard.py`): built once per run by code and kept with the run (`ctx.memo`), sent with every plan request (about 1,500 tokens): for each column its display name, type, role, meaning, share missing, the range of a number or date, the distinct count, and for a low-cardinality category or yes/no column the 15 most common values with counts and shares. A wide table keeps the columns most relevant to the request and the goal and says how many it left out. **Privacy:** no values for id or free-text columns, nor for any column that looks personal (a name or contact word in its name, e-mail addresses, phone numbers, long text, ID-like codes, people's names, or nearly every value different); those get only the distinct count, the share missing and a plain reason. The cost: a category whose values are several two-word capitalised labels is withheld like a name column; the lookup tool can still count them. Each card line is a fact with an id (`d1`, ...), so an answer about the data can cite it and its figures are checked: an empty plan with a `reply` that cites a card line is shown as the answer, with no tool call.
1. **`data_catalog`** (one module, registered like the others): the AI proposes search terms (the user's words, synonyms, local usage, spelling variants) and a lookup; code searches column names, display names, meanings and the actual values of text columns (case-insensitive, substring and fuzzy match) and answers "Yes: column X contains <value> in n rows (p%)", "Yes: the data has a column X (<meaning>); p% of its values are missing" (and says when it is mostly empty), or "No: no column or value matches ...; the closest columns are A and B". Also `columns`, `values` (at most 30 distinct values, or only the distinct count for a withheld column) and `missing` (one column or all). Every figure is a computed count; the AI never receives a row.
2. **Fallback before refusing:** an empty or unusable plan, or a model that answered with something that is not a plan, goes to the rule router, then the card reply, then the catalog on the content words of the request. The catalog answers only a request that asks about the data (it names the data, a column, a record, or asks "is there ... / do you have ..."); any other request that fits no tool is still refused. The no-AI path uses the catalog too.
3. **Refusals** always show exactly two concrete chips (of the request's own kind, padded with general ones) and no capability paragraph; the sentence says "Here are two changes I can make / questions I can answer / things you could ask" to match. The margin check no longer intercepts a question about whether the data holds something.

Tests: `test_data_catalog.py` (21: the card holds no rows and respects the cap and trims by relevance; personal-looking columns (names, e-mails, phones, codes, addresses) never appear; the catalog finds a concept by value, name and meaning, says a clear No with the closest columns, handles spelling variants and synonyms for five unrelated concepts, reports the missing share, every figure equals the pandas count, the prompt payload holds no raw row or personal value, the empty and invalid plans fall back, a value in the card is answered with no tool, five kinds of refusal show two chips). 14 catalog requests were added to `tests/lens_eval/requests.jsonl` (now 150; the scripted replay is 100% in `scripts/lens_eval_scripted_result.txt`). Existing assertions changed: `test_lens.py` (the prompt now carries the card, so category values appear with their counts; identifiers and a row's own figures still never do).

**NOT tested with the real AI:** which search terms a real model proposes for a concept, how often it answers from the card instead of calling the catalog, and how the 1,500-token card trims on a real wide table.

## Fixes from the first real-AI evaluation

Everything below was done with the fake AI and the real DuckDB; nothing is written for one request, column or value.

1. **`custom_analysis` crash** ("That step failed unexpectedly"). Reproduced first: the validator and executor passed every SQL family tried (median, quantile_cont, percentile, stddev, variance, count distinct, avg/min/max/sum, date_trunc, strftime, year/month, CASE WHEN, COALESCE, ROUND, RANK/SUM OVER, ORDER BY, LIMIT, HAVING, CTEs) on a tidy table. The crash came from the table: a column of a type DuckDB cannot read (period, interval, category, mixed or nested objects, time zones) made every query raise inside the database set-up. Fix: `sqlguard.prepare_frame` turns those columns into text (decimals into numbers) before the table is registered; any parser or set-up failure becomes a refusal with a plain sentence; unhashable cell values no longer break the data card or value matching. Every failure kind has its own plain message (`agent/errors.py`; "failed unexpectedly" is never shown), the failing SQL and the sanitised error go to `lens_errors.jsonl` in the run folder, and the repair attempts get the real error text. Tests: `test_sql_families.py` (115; each function family on a tidy and a messy table, every dangerous pattern still refused, the median-per-region request through chat).
2. **Empty plans.** A why/how-come/cause request with an empty plan now runs the new `why_breakdown` tool instead of refusing (an unrelated "why" is still refused with two chips). Every tool description starts with when to use it (why-breakdown, chart edits on the previous answer, view shortcuts such as only the charts that support an action, the data catalog). The prompt no longer says a chart cannot be made; "data then change to its chart" is one plan, `data_query` then `chart_edit`. Tests: `test_fixes_eval1.py` (scripted planners).
3. **Definitions.** "Which definitions did you use" lists the report's "Definitions used" and the user's saved definitions (`records.definitions_lines`), and says plainly when there are none. Tested with and without saved definitions.
4. **Evaluation scored by outcome.** `tests/lens_eval/requests.jsonl` (150) gained, per request, `outcome` (the expected kind: chart, table, text, refusal, view change, brief, export, question; figures traceable; no internal terms) and, for 17 requests that have several valid plans, `acceptable` (the other plans) with `several_valid`. `scripts/lens_eval.py` now reports PLAN, OUTCOME and RAN separately per category; every acceptable plan is also run and must give an acceptable outcome. The outcome check found one real leak (the "how it was calculated" note showed an internal operation name), now plain wording. New options: `--sample N` (round-robin across the categories) and `--list` (print the chosen requests, no AI). Result: `scripts/lens_eval_scripted_result.txt`, 100% / 100% / 100%. Tests in `test_lens_eval.py` (outcome checks catch an untraceable figure and an internal term, a different valid plan passes, `--list` calls nothing).
5. **Cost per request.** `ai_usage.json` now has, for each planning call, `input_by_part`: system text, data card, fact sheet, item list, history, other (tokens estimated at about 4 characters each, scaled to the provider's count when one is given).
