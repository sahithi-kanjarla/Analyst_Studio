# Build log: fixes from the real-AI run on a Shopify-style order-line file (branch `studio-v3-fix`, from `studio-v3-data`)

Fake AI only; every figure is still computed by code; no calculation was changed. Commit messages follow the attribution rules of this session. Nothing is named for an example column, audience or request.

## Done

1. **Reliable AI JSON** (`llm.py`). The model is asked in its provider's JSON mode where there is one (Groq/OpenAI-style `response_format`, Gemini's JSON mime type, Ollama's `format`); if the provider refuses the mode the call is repeated once without it and the provider is remembered. The first valid JSON object is taken from the reply: code fences, `<think>` reasoning (closed or not), and prose before or after are ignored; a cut-off reply is recognised and said so. `ask_json_ex(..., validate=...)` checks the shape the caller expects; a reply that is not JSON, or has the wrong shape, gets exactly one repair ask that shows the model what was wrong and what it sent (`ask_json` does this; the stages with their own loop, such as the plan and the understanding record, keep theirs and now get the specific parse reason). The page's trust label shows "AI partly unavailable: <stage names>" (new `ai_partly` field on the report page, a pill next to "How sure we are"); the decision log and report notes already named each fallback and its reason. Tests: `test_ai_json.py` (fenced JSON, leading prose, reasoning, truncated JSON, valid on the second try, shape errors shown on the retry, JSON mode used and dropped when refused, failed replies not saved).
2. **Rate limits.** Per-minute limits: the retry-after hint is read (header, or milliseconds), waited for with a 60 s cap, and the call is retried up to **2** times (was 3) before the stage falls back and says why; a per-day limit is not retried. Pacing to the provider's per-minute window was already in place (Groq's window by default) and is unchanged. Tests: `test_ai_json.py`, and the three older rate-limit tests updated from 3 retries to 2.
3. **Tokens per run.** Measured by `scripts/ai_tokens.py` with a fake model that answers every call with `{}` (the worst case: every stage takes its one repair and then falls back), counted at about 4 characters a token, the same on every machine. Reductions, all generic: a leaner column summary for the understanding stage (values without counts, no quartiles or rare values or date parts); one repair (not two) for the understanding stage and shorter echoes of a rejected answer; the findings sent to the critic, the insight writer, the strategy writer and the summary are fewer and cut to their first sentences (the checks still read the whole text); the clarifying-questions stage sends only the columns its signals name; the answer-picking stage is skipped when the rules already match every question; the analyst-brief stage is skipped for an exploratory run that names no KPI and describes no business; the data-quality stage's fact sheet is smaller. Not done: merging stages into one call (the replies are validated separately, so a merge could not fail one part alone) and caching beyond what exists (identical calls are already answered from the run's memory and from disk). Per-stage totals now go to `ai_usage.json` (`by_stage`), to the run log ("AI usage: ...") and to the report's technical details ("Biggest stages"). `test_token_budget.py` fails if the 12-column fixture run exceeds `AI_TOKEN_BUDGET` (default 40,000).

4. **Order-line files.** The order key is found from how values repeat, not from a name: a column whose values repeat, where a date or an additive amount is the same on every row of the same value while at least two other columns change (`grain.structural_key`); a column named like an order key is still recognised. The order count is a tile next to the first figure ("Orders", 320 on the fixture); an order's own amount repeated on each line is counted once; identical rows inside such a file are kept (two of the same product in one order are two lines); the quantity and price are taken from the line-level columns only, so the existing "revenue = quantity x price" derivation works with few distinct prices; products are ranked by that line value and the order's own amounts (subtotal, tax, total) are not split by product. Tests on the fixture: 320 orders and 640 lines, products ranked by line value equal to pandas, the key found after the columns are renamed, a customer column is not an order.
5. **Labels.** A column named like a status, or whose few values are states (paid, pending, refunded, open, closed), is a status: the rules' questions say "How does revenue differ by status (Financial Status)?" and use each column's own name (underscores as words) instead of "segments"; the plan prompt says so, and a model plan whose question calls a status column a segment is sent back; a summary sentence that uses a grouping phrase no column gives ("customer segments") is dropped with the reason. A question about time is answered by a trend (or a change between periods) over a date column, never by a split by another column; if the run has none, it says "this run has no usable trend: no date column with enough periods to follow over time".
6. **Lens misses.** (a) "only needed charts" is added to the commands when the request says it and the model left it out, so it applies when the short view is already on, and the answer says what changed (a command that changed nothing is not said first and not said twice). (b) "show that as a line" changes the latest chart in the conversation; with none, `chart_edit` asks which of the report's redrawable charts is meant (2 or 3 choices) instead of refusing; a plan that skipped it is sent back once. (c) "X and then make that chart a share chart" is checked: a plan without the chart-change step, or with a clarify, is sent back once with the reason. Tests: `test_lens_misses.py`.
7. **Eval.** "Why is X the top segment" requests accept the premise check with the report's facts, the premise check with a breakdown, or the breakdown, and an answer that corrects the premise in words; typo requests and "does the data have information about X" are scored by the answer (it must name the right figure or column) whatever the plan; `scripts/lens_eval.py` prints the total tokens, forces UTF-8 output (a console that cannot show a character prints `?`), and writes the result file before printing. Scripted result: plan 100%, outcome 100%, ran 100%.

## Decisions

- The rule-based question text keeps "segments" for ordinary category columns and says "status" for status columns; the real display names are used either way.
- A time question with no trend stays unanswered with a reason: a split by city is not an answer to it.
- The analyst-brief and answer-picking stages are skipped only under the narrow conditions above; any run that names a KPI or describes the business still asks the model.
- The 40k target is checked on the fake's counts, as asked; the budget is an environment setting.

## Result

Frontend build passes (one new pill on the report page). Full suite: the first run gave 1234 passed and 4 failed (an old repair-wording test, the old 40-item/160-character pick cap, a summary test that expected the model to be asked when the rules were already sure, and the Shopify-style report check, which found that a line's revenue split by an order's status was dominated by the blank rows of the extra lines). Fixes: the repair message says "not valid JSON" again; the cap tests use the new cap (24 items of 140 characters); the summary test makes the rules find nothing so the model path is tested; and an order's words and dates are now filled down to its lines (`grain.fill_order_details`, logged), which also lets lines be split by their order's status or date. **Second full run: 1239 passed, 0 failed, in 11 min 9 s (670 s; 673 s wall clock).**
